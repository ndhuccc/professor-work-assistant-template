# 教授端研究生週報與 GitHub 證據審查

以繁體中文，回答「本週完成了什麼、證據在哪裡、舊待辦如何、需要誰做什麼」。先給重點，再給逐生可追溯細節。所有審查文字必須遵守以下白話規範。

## 強制規範：用簡單語句撰寫審查報告

- 以不懂 Git 版本控制、也沒有深厚深度學習背景的大學部學生為閱讀基準。所有審查草稿、正式報告、摘要、表格、圖說及給學生的指引均適用；不得因讀者是教授而省略解釋。
- 使用日常用語與短句，一句盡量只說一件事。先說概念與實際意思，再視必要補上英文名稱；避免用術語、縮寫、代號代替說明。
- 不必要的術語直接改寫。確有需要時，在首次出現的同一句或緊接的括號中解釋其含義或用途，包括專有名詞、英文縮寫、方法名稱、指標與任務代號。只展開英文全名不算解釋；表格、圖說及可單獨閱讀的摘要也須就地解釋，不能只依賴文末詞彙表。
- 每項問題依序說清楚「發現什麼問題 → 為何重要 → 接下來做什麼 → 如何確認完成」。區分已查核的結果與建議的驗證方法；不得把建議寫成已完成，也不得自訂期限或驗收條件。
- 主文用可理解的工作名稱與來源連結文字，例如「本週資料整理的修改紀錄」。原始版本識別碼、任務編號、分支名、路徑與命令集中於清楚標示的「證據與技術細節附錄」，逐項對應主文；需要顯示代號時，就地說明它代表什麼。不得遺失原編號、精確來源位置或跨週追蹤關係。
- 簡化語句，不簡化或削弱研究判斷。保留重要發現、原始數值與單位、比較條件、證據來源、限制及不確定性；必要技術細節移至附錄並連回主文，不得省略或改寫成更肯定的結論。
- 交付前逐段進行可讀性檢查：上述讀者能否理解進度、問題、理由、下一步及完成確認方式？檢查主文、表格、圖說、附錄與連結文字有無未解釋名詞或代號；未通過先改寫，不得交付。

寫法示例（僅示範用語，不新增研究規準）：
- 避免：「缺 baseline，無法驗證 gain。」改為：「目前沒有在相同條件下與原有方法比較，因此還不能確認新方法是否更好。建議補上兩種方法在相同資料上的結果，並列出差異，供教授確認。」
- 避免：「無 PR，進度不足。」改為：「這週沒有送出合併請求（PR，即請他人檢查並合併修改的提案）。這不代表沒有進展；仍須查看直接保存的修改紀錄，再與本週研究目標核對。」

## 1. 核對來源與範圍

- 先重用已核准的名冊、Repo 對應、研究規準、週次／時區、教授審查來源、分支及比較基準；不要每週要求教授重貼已可取得的資料。
- 當前使用者明確核准的新版來源優先；其次用專案核准紀錄。完整操作來源見 [原指引與版本](references/source-guide.md)；排程、補充提問及檢查表見 [原指引續篇](references/source-guide-continuation.md)。不得用較舊外部副本覆蓋使用者更新版本。
- 使用此技能擁有者的既有研究室時，讀 [正式名冊設定方式](references/roster-configuration.md)。正式名冊必須由當前使用者提供並存於私人位置，本範本不含原作者名冊。Repo 擁有者／提交者不是學生 GitHub 身分的證明。
- 分別確認「身分與對應已核准」和「來源現在可讀」。不可讀不等於不存在；不繞過拒絕或改用別人的帳號。
- 缺少或衝突的身分、Repo、版本、週次或比較基準，列出已查範圍與候選，暫停受影響判定並集中詢問；繼續不依賴該項的唯讀整理。找不到核准規準時，不正式評分或下研究是否合格的結論。
- 不把個別學生某次日期、Issue 編號、放寬的論文標準或研究方法寫成全體通則。若有個案規準，記錄適用人、期間、核准者與來源。

## 2. 建立證據索引

在核准範圍自行尋找最新及上週週報、研究計畫、資料／設定版本、結果與實驗紀錄、本週 PR 或 commits，以及教授前次決定與全部未結案待辦。

逐項留下學生代號、來源檔案／連結、日期、段落／行／圖表位置、版本或 SHA。標明哪些來源已讀、缺漏、權限不足或彼此矛盾。所有列入本次範圍的學生都要有結果，不能靜默略過。

不要只摘要學生聲稱。建立「聲稱 → 實際證據 → 核准完成條件 → 可支持的判斷 → 缺口與下一步」鏈。查核研究問題、方法、資料切分、樣本數、參數／重複次數、比較基準、單位及指標算法，保留失敗、限制與不確定性。

分開標示：
- 事實／已確認：來源直接支持的內容；「學生自述完成」只能證明其聲明
- 推測／可能：明列推理依據及不能排除的解釋
- 尚待確認：尚缺的證據及誰可補充

未找到證據不等於學生未做；沒有 PR 不等於沒有進展；commit 數、更新時間及行數不等於研究品質。

## 3. 接續所有跨週事項

只用教授核准的審查紀錄與決定辨認要求，不把學生計畫、口頭轉述、AI 建議或未核准草稿提升為教授命令。

逐項沿用原編號，包含早於上週且本週未提到的待辦。保留首次提出日期、教授決定與來源、負責人、具體工作、完成條件、原核准期限、本週回應、證據、前次與本次建議狀態。

- 無核准期限：填「未設定」，不可自訂日期或判逾期
- 有完成證據但未有教授確認：填「已提出完成證據，待教授確認」
- 正式結案、取消、延期或變更條件：必須有相應教授決定來源
- 缺少前次紀錄：填「跨週追蹤待確認」，列搜尋範圍；不能假定以前沒有要求或全部已結案

不因本週沒提及而刪除、重編或重複新增舊任務。新建議與既有要求分開。

## 4. 查核 PR 與直接 commits

1. 核對 Repo、分支、時區、週次及前次已保存的 SHA；優先從該 SHA 比較至本次 SHA。缺少 SHA 時，只按已約定日期界線查核，寫清楚比較方式。
2. 有 PR 就讀目的、diff、討論與實際測試紀錄；沒有 PR 就查核核准分支上的直接 commits，不要求補開 PR 才能審查。
3. 留下 PR 連結／commit SHA 與連結、分支、日期、起訖 SHA 或精確時間範圍、變更檔及 diff 位置。對照研究工作與舊待辦，關聯重複來源，不重複計算同一變更。
4. 用白話說明改動前後、影響的研究流程、證據及疑點。不默認只看 main／預設分支，不無限擴大範圍。
5. 區分「已執行且有紀錄」「紀錄顯示未執行」「本次未見測試證據」「Agent 本次未執行」。不能把沒有 log 寫成已通過，也不能直接斷言學生從未測試。
6. 預設只讀，不執行不熟悉程式或改學生檔案。需要重現實驗時另確認環境、資料、命令、成本及授權；測試可能寫入檔案，不屬自動唯讀查核。

## 5. 交付與行動界線

使用 [逐生審查格式](references/review-template.md)，依強制白話規範撰寫並通過可讀性檢查後，先提供本週重點／最大風險／需要教授決定的一頁摘要，再附逐生證據與跨週表。對每個缺口給具體可回答問題、所需檔案／數據／驗證方式；不要只寫「補完整」。

教授做最後研究判斷與對學生的決定。輸出中的狀態先是建議草稿，不代表已改外部任務或正式紀錄。

- 草擬不等於存檔。需存檔時，先確認內容與教授約定位置，例如 professor-reviews/；不得直接改學生研究檔案
- 尊重「各自管理自己的資料夾」約定即可；不主動建立技術隔離、權限系統、分支保護或 CODEOWNERS
- 存檔不等於發送。留言、Issue、通知學生、合併、推送或分享均分開核對本次明確授權、對象、內容及目的；遵守所用工具確認規則
- 建立技能不會建立排程。只有教授明確要求時，才另確認時間、時區、來源、輸出位置及通知條件，並驗證排程保存

## 交付前自查

逐生覆蓋完整；每項重要判斷有來源；事實／推測／未知分開；所有舊待辦持續；無擅改期限或結案；無 PR 時已查 commits 或明列阻礙；測試狀態忠實；研究規準適用；只有核准的輸出或外部行動。

必須另通過可讀性檢查：以不懂版本控制、深度學習背景有限的大學部學生為基準；語句簡短；必要術語、縮寫與代號首次出現即有白話解釋；每項問題的原因、下一步與確認方式清楚；表格與圖說可單獨理解；技術細節與主文有對應；數值、單位、限制、未知與來源完整。任一項未通過，先修正，不得交付。
